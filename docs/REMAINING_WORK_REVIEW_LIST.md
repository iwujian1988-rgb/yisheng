# 剩余工作与 Review 清单

> 日期：2026-06-08  
> 目标：把当前 MVP 收口到可真实试点、可交给资深小程序开发和后端架构师审查的状态。

## 1. 本地已完成

- 小程序 152 个注册页面路由完整。
- OCR/ASR/手动输入/模板草稿可以进入确认或首页链路。
- 后端已有 auth、admin、purchase、device、history、template、AI/OCR/ASR gateway。
- 管理员登录、激活码导入、用户激活、设备预置、proofCode 校验、设备绑定、用户态刷新已有 smoke 覆盖。
- 后台 `/admin` 页面已清理乱码，支持设备单台预置、批量导入、CSV 模板下载。
- 小程序设备管理页、设备详情页、后端检查页、网络测试页已接入真实服务层。
- OCR worker wrapper、PaddleOCR/RapidOCR adapter、单图测试 CLI 已具备。
- OCR/ASR 结果必须先进确认页，用户可编辑后再进入草稿。
- 历史记录只保存加密 payload 和 metadata，不保存明文。
- 生产环境默认禁止 `STORE_MODE=file`。
- 设备 proofCode 后端哈希存储和校验，前台/后台不暴露哈希。
- 一键交付前检查：`npm run release:check`。

## 4. 给资深小程序开发的 Review 问题

1. OCR/ASR 用临时 storage key 传结果到确认页，在目标基础库和真机上是否稳。
2. 首页草稿来源从 OCR/ASR/模板/手动切换时，页面生命周期是否会吞草稿或重复保存。
3. 3000 字长文本页面、textarea、滚动、返回栈是否有卡顿或兼容风险。
4. 设备管理页的绑定、解绑、重新检测路径是否符合小程序真机交互习惯。
5. 后端检查页的信息是否足够现场人员定位配置问题。

## 5. 给后端架构师的 Review 问题

1. 当前 API contract 是否足够支撑第一批试点。
2. file store 到 MySQL/RDS 的迁移边界是否清晰。
3. 生产禁止 file store 的策略是否应强制，不允许灰度开关。
4. proofCode 用 PBKDF2 哈希是否足够，是否需要改为一次性挑战码或硬件签名。
5. 设备预置、激活码、用户开通、审计日志是否满足最小运营闭环。
6. `/api/health` 暴露的配置状态是否足够且不泄露敏感信息。
