# 快速高质量收尾开发路线

> 日期：2026-06-08  
> 目标：尽快把当前本地 MVP 骨架推进到可真实试点的版本，同时守住医疗文本安全、硬件传输稳定和可验收质量。

## 1. 总策略

不做“大而全”的重构。接下来只打 4 条主线：

1. **真实后端闭环**：登录、激活、设备绑定、历史、管理员操作走后端稳定接口。
2. **OCR 闸门闭环**：PaddleOCR/RapidOCR 能跑小样本，结果必须进入用户确认页。
3. **硬件传输验收**：3000 字 / 120 秒真机压测，有记录、有失败归因。
4. **上线安全闸门**：日志不泄露正文，管理员不看明文，AI/OCR/ASR 不绕过确认。

## 2. 角色分工

### Codex 负责

- 后端 API、worker、服务层、加密/脱敏、安全边界。
- 小程序核心链路接入和 bug 修复。
- 测试脚本、smoke、验收闸门。
- 代码 review 和质量把控。

### 廉价 AI 负责

- 文档整理、测试材料、记录表、失败归因初稿。
- UI 页面静态文案检查。
- TODO 汇总和低风险清单整理。
- 不允许改 `services/**`、`backend/src/**`、`utils/ble/**`、`utils/encoder/**`、`app.json`。

### 人工/真机负责

- OCR 图片样本拍摄和人工标注。
- 医院/目标电脑环境测试。
- 硬件 3000 字压测。
- 微信小程序真机端到端验收。

## 3. 最快推进顺序

### Phase A：OCR 闸门跑通

目标：不是追求最终准确率，而是确认 OCR 可以进入主链路。

交付：

- `backend/workers/ocr-worker.example.js` 可调用 PaddleOCR/RapidOCR adapter。
- `backend/workers/adapters/*` 可部署。
- `docs/ocr-gate-test-plan.md` 和 `docs/ocr-gate-test-materials.md` 可执行。
- 3-5 张样本跑出结果。

通过条件：

- S-01 清晰中文在 PaddleOCR 上通过。
- 5 张中至少 3 张 PaddleOCR 通过。
- 所有结果进入用户确认页。
- 无日志正文泄露。

### Phase B：真实后端试点闭环

目标：摆脱纯本地 fallback，形成一套可试点后端。

交付：

- 后端启动脚本和环境变量说明。
- 管理员创建/激活用户流程验证。
- 设备绑定、解绑、权益查询验证。
- 历史记录只存 ciphertext/envelope。

通过条件：

- `node backend/scripts/smoke.js` 通过。
- 管理员 API 不返回用户正文。
- 普通用户端能完成登录 -> 激活 -> 绑定 -> 首页。

### Phase C：3000 字硬件压测

目标：证明核心价值能稳定跑。

交付：

- 3000 字非医疗文本生成。
- 发送耗时记录。
- 失败原因记录。
- 设备/电脑环境记录。

通过条件：

- 3000 字在 120 秒内传输完成。
- 目标电脑上屏内容可核对。
- 失败时有明确归因：蓝牙、输入法、速度档、电脑环境或文本问题。

### Phase D：试点前安全验收

目标：避免“能跑但不能放心跑”。

交付：

- 安全检查清单。
- 日志字段检查。
- AI/OCR/ASR 用户确认链路检查。
- 管理后台明文隔离检查。

通过条件：

- 管理端不可见用户正文明文。
- OCR/ASR/AI 不直接发送、不直接进入下一步。
- 日志不记录图片、音频、OCR/ASR/AI 正文。

## 4. 当前立即动作

1. Codex 继续补 OCR 运行/部署脚本和端到端测试入口。
2. 廉价 AI 制备 OCR 样本，按 `ocr-gate-test-materials.md` 填基准文本。
3. 人工准备目标电脑和硬件，预约 3000 字压测环境。
4. Codex 跑现有后端 smoke，保持每次核心改动都有验证。

## 5. 不做事项

为了速度，以下延后：

- 复杂表格结构化还原。
- 手写体识别。
- 大规模 OCR 准确率测试。
- 多租户后台复杂权限矩阵。
- 大型 UI 重设计。
- 自动 OCR 引擎动态降级策略。

这些都不影响试点闭环，等核心链路跑通后再排。
