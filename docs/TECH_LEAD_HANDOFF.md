# 病历传输小程序技术接管说明

## 1. 当前最高优先级

当前最高优先级是完成 PRD 中的小程序部分，并优先保证核心链路稳定：

1. 用户登录/注册/账号体系从 0 到 1 建立。
2. 登录、注册、微信登录时必须判断用户是否已购买硬件或已被后台开通。
3. 后台需要支持创建、导入、查询、禁用付费用户/硬件用户。
4. 蓝牙连接、文本编码、分片发送、进度、取消、错误恢复形成可复用核心模块。
5. 达成 3000 字在 2 分钟内稳定传输的验收目标。
6. 医疗文本存储采用用户侧可读、管理员不可明文查看的加密设计。
7. OCR、ASR、AI 能力接入前先定义脱敏和数据边界。

页面完整度重要，但在本项目里优先级低于“真实医院电脑可稳定上屏”。

## 2. 技术总监职责边界

Codex 负责：

- 项目初始化与架构设计。
- 全局代码规范、目录规范、状态管理规范。
- 蓝牙核心链路封装：设备发现、连接、服务/特征发现、发送队列、分片、重试、取消、进度、日志。
- VUC/token 编码规则和协议适配层。
- 长文本稳定性、复杂 bug 排查、真机联调策略。
- 账号体系、付费用户/硬件用户开通逻辑、数据加密、脱敏、AI/OCR/ASR 接入架构。
- 小程序内所有核心 AI 交互和内容生成逻辑。
- 代码审查与合并把关。

低成本 AI 负责：

- 已明确交互的普通页面开发。
- 静态 WXML/WXSS UI 还原。
- 表单校验、空状态、列表页、个人中心页面。
- 帮助中心、教程页、协议页、FAQ、购买记录页等低风险页面。
- 根据已有组件和规范补齐重复页面。

低成本 AI 不允许独立修改：

- 蓝牙发送主链路。
- VUC/token 编码规则。
- 加密、脱敏、登录鉴权。
- 付费用户校验、硬件购买状态、后台开通逻辑。
- 与 DeepSeek、OCR、ASR 相关的数据出入边界。
- AI 对话、模板生成、医学内容生成、病历整理等核心提示词和结果处理逻辑。
- 全局路由、全局状态、核心配置。

## 2.1 已调通代码保护原则

GitHub 当前代码已经完成核心链路调通，后续修改必须遵守：

- 不直接重写已经跑通的蓝牙/VUC 主逻辑。
- 优先通过模块封装、测试补齐、参数化、日志增强、性能优化来演进。
- 每次优化前必须明确保留原有行为。
- 关键发送逻辑需要保留回退路径。
- 便宜 AI 不允许接触已调通核心逻辑。
- Codex 修改核心逻辑时必须先做代码审查说明，再小步提交。

这意味着后续第一轮工程化不是“推倒重写”，而是把现有可用逻辑提炼成稳定模块。

## 3. 目标硬件协议

硬件固件协议暂时锁死，小程序端必须适配现有协议。

当前协议核心：

```text
SPD2|WIN11|<payload>
```

约束：

- 不以“改固件”为默认解决方案。
- 通过小程序端流控实现稳定性。
- 汉字和中文标点转为 VUC token。
- 长文本必须经过原子 token 队列发送。
- 微信 BLE 写入需要按 MTU 分片，默认按 20 字节保守处理。

## 4. 长文本验收目标

核心验收目标：

```text
3000 字内容可以在 2 分钟内传输完成，并在目标电脑稳定上屏。
```

这意味着平均吞吐需要达到约 25 字/秒。但 VUC 汉字若固定 180ms/字，只能达到约 5.5 字/秒，无法满足该目标。

因此后续必须做自适应流控：

- 普通 ASCII、数字、英文单位使用更短延迟。
- 汉字 VUC 使用动态延迟，而不是永久固定 180ms。
- 根据目标环境提供速度档：安全、均衡、极速。
- 支持试发校准：用短文本探测当前电脑/输入法承载能力。
- 失败后可降速重试。

## 5. 医疗数据合规边界

产品允许存储病历文本，但必须满足：

- 用户可查看自己的内容。
- 管理员不可明文查看用户病历。
- 服务端数据库中病历正文必须加密存储。
- 调用第三方 AI 前必须脱敏。
- 日志、埋点、错误上报不得包含明文病历。

建议实现方向：

- 用户级内容密钥或信封加密。
- 服务端只存密文和必要索引字段。
- 客户端显示前解密，或由受控服务端在用户授权上下文中解密。
- AI 调用前执行姓名、手机号、身份证、住院号、病案号、地址等脱敏。
- 保留脱敏映射只在本次会话内使用，默认不持久化。

## 5.1 付费用户和硬件售卖边界

商业模式是售卖硬件，因此账号体系不是普通开放注册，必须绑定购买/开通状态。

登录、注册、微信登录后需要判断：

- 该用户是否已经购买硬件。
- 该手机号/微信 openid 是否在后台开通名单中。
- 该用户是否绑定过设备。
- 该设备是否被其他账号绑定。
- 该账号是否仍处于有效服务期。

后台需要具备：

- 创建付费用户。
- 批量导入购买用户。
- 查询用户购买/开通状态。
- 绑定硬件设备序列号。
- 禁用用户或设备。
- 查看非敏感使用状态，例如最近登录、设备连接次数、传输次数。

后台不得具备：

- 直接查看用户明文病历。
- 直接查看用户传给 AI 的原始医疗文本。
- 导出明文医疗内容。

## 6. AI/OCR/ASR 初步选型原则

OCR：

- 优先寻找开源免费方案。
- 小程序端直接跑 OCR 的能力有限，优先考虑服务端 OCR。
- 候选方向：PaddleOCR、RapidOCR、Tesseract。
- 医疗场景中文识别优先考虑 PaddleOCR/RapidOCR。

ASR：

- 若要求免费开源，优先考虑 Whisper/faster-whisper 服务端部署。
- 若要求低延迟和小程序易接入，可评估微信同声传译插件或云厂商 ASR，但成本和隐私要单独评估。
- 医疗术语准确率要通过自有测试集验证。

AI：

- 使用 DeepSeek V4。
- 所有请求必须经过脱敏网关。
- AI 输出进入发送链路前要经过用户确认，不自动传输到电脑。
- 小程序内 AI 对话、模板生成、病历整理、报告整理、内容润色等核心逻辑由 Codex 负责设计和审查。
- 低成本 AI 只能做 AI 页面外壳和静态交互，不允许独立编写核心提示词、脱敏策略和结果处理逻辑。

## 7. 下一阶段推荐路线

第 1 阶段：架构整理

- 建立 `utils/ble` 或 `services/ble` 核心模块。
- 建立 `utils/encoder` VUC/token 编码模块。
- 建立 `services/auth` 账号模块。
- 建立统一错误码和日志策略。
- 将首页中的蓝牙逻辑从页面文件拆出。

第 2 阶段：MVP 小程序

- 登录、注册、找回密码。
- 首页文本输入、蓝牙连接、发送进度、取消发送。
- 设备管理基础页。
- 历史记录基础页，内容加密存储。
- 传输设置：速度档、系统模式、校准。

第 3 阶段：能力增强

- OCR 上传识别。
- ASR 录音转写。
- DeepSeek 脱敏调用。
- 模板库和 AI 对话。
- 会员和支付。
