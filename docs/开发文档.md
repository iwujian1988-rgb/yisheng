## 1. 项目定位

本项目是一个“文本传输助手”微信小程序，核心能力是将用户准备好的文本，通过专属蓝牙硬件发送到电脑端，由硬件模拟键盘输入到目标系统中。

产品原始场景偏医疗病历传输，因此必须特别关注：

- 医疗文本不能进入普通日志、埋点、后台明文展示。
- AI/OCR/ASR 调用前必须经过脱敏或受控网关。
- 管理员只能管理用户、设备、服务状态，不能直接查看用户明文内容。
- 已验证可靠的蓝牙/VUC 发送链路是核心资产，后续不能推倒重写。

当前商业模型以硬件售卖和服务开通为核心：

- 用户登录后不能直接进入全部功能。
- 需要判断是否已购买、是否已绑定设备、服务是否有效。
- 非会员或未开通用户只能进入引导、购买、绑定或客服流程。
- 会员/有效用户才允许使用完整的 AI、OCR、ASR、模板和发送链路。

## 4. 核心功能模块与实现逻辑

### 4.1 登录、账号与权限

目标逻辑：

```text
手机号验证码登录
  -> 手机号不存在时自动注册并生成永久 user.id
  -> 手机号已存在时复用原 user.id
  -> 默认绑定当前微信 openid
  -> 后端返回 user、token、purchaseStatus、deviceBindingStatus、serviceStatus
  -> 小程序根据状态决定去购买页、绑定页、账号状态页或首页
```

当前确认的账号规则：

- 手机号是用户账号，唯一。
- `user.id` 是用户唯一识别码，首次注册时生成，后续不会变化。
- 后续如果用户更换手机号，只修改 `phone`，不能重建用户或更换 `user.id`。
- 验证码登录是主流程，手机号未注册时自动创建账号。
- 当前验证码默认固定为 `123456`，后续短信接口申请完成后再替换为真实短信服务。
- 微信登录只允许已绑定微信的账号登录。
- 未绑定微信点击微信登录时，应提示“微信未绑定账号，请用手机号验证码登录”。
- 手机号已绑定其他微信时，应拒绝登录并提示联系客服解绑。
- 当前普通用户不需要设置密码；密码登录仅作为兼容/备用能力保留。

- `services/auth/session.js`：登录 session 归一化和本地持久化。
- `services/auth/dev-auth.js`：本地测试账号。
- `services/auth/guard.js`：页面访问保护。
- `services/constants/account-status.js`：账号、购买、绑定、服务状态常量。
- `services/api/client.js`：统一 API 请求封装。
- `backend/src/modules/auth.js`：手机号验证码登录、自动注册、微信绑定、微信登录校验。

### 4.2.1 通用内容可见性配置

目标：把“游客、审核员、未连接设备用户不能看到专业/医疗内容”的判断做成公共能力，避免模板、快捷操作、智能创作、AI 网关各自写一套权限逻辑。

当前公共模块：

- `backend/src/security/content-access.js`

核心设计：

```text
内容项
  -> audience: general | professional
  -> status: published
  -> 按业务配置读取 capability
  -> 按可见条件判断是否返回给当前用户
```

默认可见规则：

| audience | 默认可见条件 | 用途 |
| --- | --- | --- |
| `general` | 不要求会员，不要求设备 session | 审核、游客、普通办公内容 |
| `professional` | 要求会员有效 + 设备 session 有效 | 专业/医疗相关内容 |

可见条件配置项集中在 `content-access.js`：

```js
const AUDIENCE_ACCESS_RULES = {
  general: {
    requireMember: false,
    requireDeviceSession: false,
    listWhenNoProfessionalAccess: true,
    capability: ''
  },
  professional: {
    requireMember: true,
    requireDeviceSession: true,
    allowConnectedBoundDeviceFallback: true,
    listWhenNoProfessionalAccess: false,
    capability: ''
  }
};
```

业务模块配置项集中在同一文件：

```js
const BUSINESS_ACCESS_CONFIG = {
  templates: {
    audienceField: 'audience',
    statusField: 'status',
    publishedStatus: 'published',
    professionalCapability: 'professional_templates',
    listMode: 'visibleAudience'
  },
  quickActions: {
    audienceField: 'audience',
    statusField: 'status',
    publishedStatus: 'published',
    professionalCapability: 'professional_quick_actions',
    listMode: 'visibleAudience'
  }
};
```

字段说明：

- `audienceField`：业务数据中区分通用/专业内容的字段，默认是 `audience`。
- `statusField`：业务数据中表示发布状态的字段，默认是 `status`。
- `publishedStatus`：只有等于该值的内容才可对用户展示。
- `professionalCapability`：访问专业内容时需要的设备 session capability。
- `allowConnectedBoundDeviceFallback`：当设备 session 暂不可用时，是否允许 `?connected=true` 且用户已绑定设备作为兼容条件。该项用于兼容现有小程序/测试流程，正式强校验可关闭。
- `listMode`：
  - `visibleAudience`：列表只返回当前场景可见的一组内容；无专业访问时返回 `general`，有专业访问时返回 `professional`。
  - `allAccessible`：返回当前用户有权访问的全部内容。

当前已接入的后端业务：

- 模板列表、模板详情、模板生成：`backend/src/modules/user-api.js`
- 快捷操作列表：`backend/src/modules/user-api.js`
- 智能创作模式和系统模板：`backend/src/modules/smart-creation.js`
- AI quick action 执行和专业 prompt 判断：`backend/src/modules/provider-gateway.js`

新增业务接入方式：

```js
const contentAccess = require('../security/content-access');

const context = contentAccess.getAccessContext({
  store,
  req,
  actor,
  businessKey: 'templates'
});

const visibleItems = contentAccess.filterVisibleItems(items, {
  businessKey: 'templates',
  context
});
```

单条内容详情或执行类接口应使用强校验：

```js
const access = contentAccess.requireItemAccess(item, {
  store,
  req,
  actor,
  businessKey: 'templates',
  deniedCode: 'TEMPLATE_ACCESS_DENIED',
  deniedMessage: 'template access denied'
});

if (!access.ok) {
  fail(res, access.statusCode, access.code, access.message);
  return;
}
```

后续如果要调整可见条件，例如“专业内容只要求会员，不要求设备 session”，优先修改 `AUDIENCE_ACCESS_RULES.professional`，不要在业务模块里写临时判断。

当前专业内容默认条件：

```text
会员有效
  AND (
    设备 session 有效
    OR (?connected=true AND 用户已绑定设备)
  )
```

其中 `?connected=true AND 用户已绑定设备` 是兼容路径。若后续要求更严格的硬件校验，应把 `allowConnectedBoundDeviceFallback` 改为 `false`，让专业内容只认设备 session。

安全原则：

- 最终过滤必须在后端完成。
- 前端可以传连接状态或做 UI 提示，但不能依赖前端隐藏专业/医疗内容。
- 专业/医疗内容必须标记 `audience: 'professional'`。
- 通用内容必须避免医疗关键词，适合游客、审核员、未连接设备用户看到。

#### 4.3.2 协议与 BLE 特征

业务包格式：

```text
SPD{n}|WIN11|<payload>
```

- `SPD1–4` 与小程序「快速 / 均衡 / 稳定 / 慢速」一一对应，固件据此设置七键间隔与空格前等待。
- 每个 VUC token 单独一包，payload 为 `VUCXXXX,`（含尾部逗号）。
- 字母 token 发两包：字母包 + 换行包（`\n`）。
- `letter → vuc` 边界额外发一包空格。

BLE UUID（Nordic UART 风格）：

```text
Service: 6E400001-B5A3-F393-E0A9-E50E24DCCA9E
Write:   6E400002-B5A3-F393-E0A9-E50E24DCCA9E  （小程序 → 固件）
Notify:  6E400003-B5A3-F393-E0A9-E50E24DCCA9E  （固件 → 小程序，ACK / 版本）
```

编码规则（`utils/encoder/vuc.js`）：

- 中文、中文标点、全角字符 → 大写四位 `VUCXXXX`。
- 英文括号 `(`、`)` 也转 VUC。
- 小写/大写字母 → `letter` token（两包 + 必要时补空格）。
- 数字及其他 → `normal` token 直发。

#### 4.3.3 速度档位（小程序 ↔ 固件联动）

配置源：`services/settings/transfer-settings.js`，固件 `applySpdProfile()` 与之保持一致。

| 小程序档位 | SPD 标签 | 七键间隔（固件） | 空格前等待 | 说明 |
| --- | --- | --- | --- | --- |
| 快速 turbo | SPD1 | 0ms（`Keyboard.print` 连打） | 5ms | 最快，需真机长文压测 |
| 均衡 balanced | SPD2 | 12ms/键 | 10ms | 速度与稳定性折中 |
| 稳定 safe | SPD3 | 50ms/键 | 20ms | 推荐日常 |
| 慢速 slow | SPD4 | 100ms/键 | 30ms | 最稳；纯中文约 **1.2 字/秒** |

**ACK 模式下实际速度由固件敲键耗时决定**，不再叠加小程序侧 180/250/350ms 字间延迟。

汉字 `VUC4E00`（7 键）粗算耗时：`45ms 重组 + 7×七键间隔 + 空格前 + BLE/ACK 往返`。

#### 4.3.4 ACK 闭环流控（当前全档位启用）

**问题背景**：早期开环方案（小程序按固定 ms 发下一 token，不等 PC/固件敲完）在短句可用、**长文（约 3000 字）易乱码、首字即错、VUC 字面量泄漏**；单纯加大延迟无法根治。

**现行方案**：全部速度档均采用 **ACK 闭环**——每发完一个逻辑包，等设备 Notify `DONE` 后再发下一包。

```text
小程序                          ESP32 固件                         Windows
  |  write 一包 (可分片)  -->  |  分片重组 (空闲 45ms)              |
  |                            |  解析 SPD|WIN11|payload           |
  |                            |  typeVucToken / 直打字符           |
  |  <-- Notify "DONE"  -----  |  notifyDone()                    |  HID 键盘
  |  收到 DONE，发下一包  -->  |  ...                             |
```

**小程序侧**（`behaviors/ble-transfer.js`）：

- 连接后 `wx.setBLEMTU({ mtu: 512 })`，尽量单包发送（汉字包约 23 字节）。
- 订阅 TX Notify，`wx.onBLECharacteristicValueChange` 监听 `DONE`。
- **ACK 锁存**：若 `DONE` 早于 `write` 成功回调到达，先 latch，避免漏 ACK 导致卡死。
- 每逻辑包发送完成后 `waitForDeviceAck()`，超时 **10s** 提示「设备响应超时」。
- ACK 模式下 `finishToken` 字间延迟为 **0**（`usesAckFlow()` 恒为 `true`）。

**固件侧**（V3.0.6+）：

- **分片重组**：`onWrite` 只追加缓冲，`loop()` 中空闲 **45ms**（`RX_IDLE_MS`）后整包处理，**每包只 Notify 一次 DONE**（修复多片包多次 DONE / 漏 ACK）。
- `typeVucToken()`：按 SPD 档位逐键 `delay(vucKeyDelayMs)`，空格前 `delay(vucPreSpaceDelayMs)`，再敲空格上屏。
- `GET_VER` 仍走 Notify 返回版本与 MAC，不走 DONE 业务 ACK。

**已验收结论**（慢速 SPD4 + ACK）：长文 **零错字**；其他档位需在目标电脑上分别做 3000 字压测。

#### 4.3.5 发送流程摘要

```text
textToTokens(text)
  -> 按 token 排队
  -> 必要时 insertSpace（letter 后接 vuc）
  -> sendPacket(createVucPacket / createLetterPackets / createPacket)
       -> str2ab -> splitBuffer(MTU，默认 20，协商后可达 ~509)
       -> 分片 write，片间 20ms
       -> 等待 Notify DONE（全档 ACK）
  -> 更新进度 / 支持取消 / 发送中常亮
  -> 不落库（隐私策略）
```

#### 4.3.6 后续可优化项（未做）

| 项 | 说明 |
| --- | --- |
| 字母双包 | 每个字母 2 次 write + 2 次 ACK，混合文本（如 G1P1）偏慢；可评估去掉多余换行包 |
| 档位压测 | 快速/均衡 + ACK 长文是否仍乱码，决定能否下调七键间隔 |
| 多 token 合包 | 一包带多个 `VUCxxxx,`，固件敲完再 DONE，可显著提速，改动较大 |
| `RX_IDLE_MS` | MTU 已 512 时可试 25–30ms，每字省约 15–20ms |
| 编辑器职责 | `pages/transfer/editor.js` 仍混有部分 BLE 职责，可继续小步拆服务 |

#### 4.3.7 开发与验收注意

- 改速度档需**小程序重编译**；改固件需**重烧 ESP32**，版本应 ≥ **V3.0.6-VMode**。
- 测试前建议断开蓝牙重连，以触发 MTU 协商与 Notify 订阅。
- 压测记录：档位、固件版本、Windows/输入法、字数、耗时、失败现象（首字错 / 中间丢字 / VUC 泄漏 / ACK 超时）。
- 发送完成后不保存用户正文（隐私策略：传输纯前端 BLE 直传，不落本地/云端历史）。

### 4.6 OCR 图片取字

目标逻辑：

```text
首页「图片识别」
  -> pages/ocr/index（唯一入口）
  -> ActionSheet 选拍照/相册（原图，>5MB 自动压缩）
  -> pages/ocr/cropper（bingli image-cropper，可旋转，角点热区 CORNER_HIT=56）
  -> 点「识别文字」裁剪完成并返回 OCR 页，自动识别
  -> 后端 DashScope QwenVL-OCR
  -> 同页行列表勾选（lines[]，默认全选）
  -> （可选）专业整理
  -> 确认使用 -> draft 回首页 inputText
```

当前实现：

- `pages/ocr/index`：选图、跳转裁剪、识别、行勾选、整理、确认（**无独立 result 页**）。
- `pages/ocr/cropper`：裁剪 + 旋转，确认按钮文案「识别文字」，经 `eventChannel` 回传裁剪图。
- `components/image-cropper`：自 bingli 移植；角点拖拽热区 56px（约 112×112 触控区）。
- `services/ocr/image-pipeline.js`：选图、压缩、跳转裁剪页（已移除 `wx.cropImage`）。
- `services/ocr/recognizer.js`：调用 `/api/ocr/recognize`。
- `backend/src/ocr/split-lines.js`：OCR 全文 `text` 拆为 `lines[]`（按换行，空则整段兜底 1 行）。
- `backend/src/modules/provider-gateway.js`：`callCloudOcr()` + `buildOcrPayload()`。

配置（`backend/.env.local`）：

- `DASHSCOPE_API_KEY`：阿里云通用 Key，OCR/ASR 共用。
- `OCR_CLOUD_MODEL=qwen-vl-ocr-2025-11-20`，`OCR_CLOUD_TASK=text_recognition`。
- 图片上传上限 5MB；前端超限会先 `compressImage` 再上传。

交互要点：

- 识别失败或未识别到文字：留在 OCR 页提示，不自动回首页。
- 裁剪/选图取消：留在 OCR 页。
- 确认前至少选中 1 行（整理模式下以 textarea 内容为准）。
- 权限与设备校验沿用现有 gateway 规则（会员 + 设备会话）。

当前完成度：

- 云 OCR + 单页行勾选 + bingli 裁剪页（含旋转）已落地。
- 角点热区 `CORNER_HIT=56`；横版单据在裁剪页先旋转再识别。
- 本地 RapidOCR worker 仍可作为无 Key 时的回退。
